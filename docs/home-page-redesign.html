The landing page that never says where you left off

Home is three horizontal carousels of identical 200×320 cards, drawn by HomePage::render into home_page(). It opens the app, and it is the only library page with no header, no counts and no state — while the one thing a reader almost always wants from it, resume the book I was reading, is a card indistinguishable from the nineteen beside it.

Third in the series. Follows the hierarchy page redesign (docs/hierarchy-page-redesign.html).

Defect. One LIMIT 20 feeds two sections. install fetches 20 recently-read rows and splits them by the 98 % threshold, so a reader who just finished twenty books gets an empty Recently read — the section the page exists for. The sections need independent limits, or independent queries.home.rs:72–89

Defect. Section title and its carousel are separated by SPACE_LG, and sections from each other by SPACE_LG — the same 18 px. Nothing binds a heading to the row it names except order.library.rs:100–106
Every Finished card carries a 100 % progress bar. The section heading already said it; the bar is the same ink on every card, carrying no difference.home.rs:34–36
book_card.rs:283

Empty sections are skipped silently, so the page's shape depends on data: a fresh library shows one row, an old one three, and neither states which is which.home.rs:100–102

Directions

All four assume the two defects above are fixed regardless of choice — independent limits per section, and the heading bound to its own body. They differ in what Home is: a shelf, a resume screen, a log, or a console.

What I'd build

B's mechanics under A's shape. A answers the question Home is for and B fixes the thing that is actually broken about it; they are compatible, because A's rails can wrap instead of scrolling and lose nothing. Ship the split-limit fix first — it is a defect, not a redesign, and today it can empty the page's most important section outright.

  1. Query in progress and finished separately, each with its own limit, instead of splitting one LIMIT 20 client-side.
  2. Bind each heading to its own body: SPACE_SM inside a section, SPACE_XL between sections.
  3. Promote the most recently read book to a hero with position, a chapter label and a primary Continue.
  4. Turn the remaining carousels into wrapping rows capped at one row, with "n of m" and a link to the full list.
  5. Drop Finished as a section; suppress the progress bar at 0 % and 100 %.
  6. Move the section titles into browsing_states with the rest of the page's copy.
  7. Give Home's grids the same BookManagement the other pages get, so right-click behaves the same everywhere.

C is worth keeping on the shelf: it is the only design that pays for the description and audiobook fields, and if those are meant to stay in the payload, something should render them. D is a different application — a library console — and should be argued for on its own, not smuggled in as a home page.

Not answered from the code

  • Is there a resumable position to show? sync_state_version keys reading positions per book, but BookCardRow carries only progress. A hero saying "chapter 7 of 19" needs the locator resolved to a chapter label — which the reader may already do on open, and I did not trace.
  • Should Home respect LibraryView? set_library_view deliberately skips Home. Direction C is essentially the detailed row applied to Home, which reopens that decision.
  • Is home_book_limit = 20 per section or per page? The contract has one number and the code spends it three ways; splitting the queries forces the question.
  • Does anything intend to consume audiobook_duration_ms? Nothing in apps/ reads it. Either C claims it or it should stop being selected.
