Backend architecture / a design proposal

One library.
More than one thing at a time.

Keep a single owner for the library. Stop making that owner wait for a whole download before handling the next request.

What happens during a slow download?

Step through the same sequence in both designs. This is an illustrative schedule, not a performance measurement.

Current / whole-operation wait

The command loop stays inside the download

Command loop
Receives DownloadBook, then awaits its completion.
Network operation
HTTP may be pending without blocking the OS thread.
Browsing, events & scan progress
Wait for the command handler to return.

The thread can run independently scheduled tasks. But this loop cannot process another command, publish events, or poll its scan/import futures while the handler is awaiting.

Proposed / owned concurrent work

The command loop starts work and returns

Command loop
Accepts the download and retains its operation and reply.
Network operation
Runs concurrently under library ownership.
Browsing, events & scan progress
Continue while HTTP is pending.

Concurrent does not necessarily mean another thread. Owned futures beside the loop or owned local tasks can both provide this behavior.

Keep ownership. Separate execution.

The actor becomes a small coordinator—not a new framework, and not a mandatory gateway for every database write.

This is a responsibility diagram, not three required threads or three required message types. Only changes to coordinator-owned state need a completion routed back to it.

Three contracts make concurrency safe

01 / ORDERING

Parallel where safe

Browsing can overlap a download. Importing into a folder that is being moved or deleted needs explicit rules and validation. Do not simply spawn every command.

02 / CANCELLATION

A caller is not the work

Closing a reader can cancel its read. Dropping a download waiter need not cancel accepted durable work. Browser shared downloads must retain their existing coordinator-owned lifetime.

03 / SHUTDOWN

No abandoned replies

Stop accepting work, close subscriptions, and resolve pending replies. Cancel or finish owned work at safe boundaries. Blocking I/O already running cannot simply be aborted.

The architectural decision is smaller than it sounds.

Keep: the library handle, library lifetime, native thread confinement, browser coordination, durable queues, and guarded commits.

Change: command handling must not await long I/O before returning to the loop. Give pending operations consistent ownership, reply cleanup, and concurrency limits.

Still to decide: per-operation ordering and cancellation contracts. Choose owned local tasks versus a collection such as FuturesUnordered after that audit—not as a substitute for it.

Important limit: async scheduling does not make synchronous work non-blocking. Slow SQL, database lock waits, filesystem calls, and CPU work can still stall the library executor. Native offloading and browser worker execution remain necessary where appropriate.
