The catalogue page where no book fits above the fold

A store catalogue page stacks five full-width bands before the first result: source identity, search, breadcrumbs, navigation links, facets. On a 700 px window that chrome is about 365 px and one publication card is 424 px (LARGE_BOOK_CARD_HEIGHT_PX). The reader scrolls to see a single book — and the band that costs the most, the wrapped navigation links, is the one they use least.

Fourth in the series. Follows home page redesign (docs/home-page-redesign.html).

Drawn by StorePage::render, apps/ui/gpui/browser/src/universal/store/view.rs:308-413. Facets have already moved from one GroupBox per axis to a row of dropdown buttons — this counts that improvement, not the pill grid it replaced.

Findings

  1. Five bands, five heights, one axis. Every control gets its own full-width row whether or not it has anything in it. Nothing shares a line with anything else, so the cost is additive and unbounded.
  2. The navigation links are the most expensive and the least used. Each folder_card is a fixed 280 px wide × 41 px tall (library.rs:431), so six links wrap to two rows at any window under ~1 700 px. They are catalogue subsections — a place to go once, not a control to keep on screen.
  3. Facet state is invisible when collapsed. The dropdown shows the active option as its label, but with three closed dropdowns there is no single place that answers "what is filtering this list right now". The active flag OPDS already sends is spent on a button label.
  4. The header repeats the rail. "← Catalogs" plus a 21 px source title plus OPDS · sv is 44 px restating what the breadcrumb's root already says.
  5. Chrome does not shrink when it is empty. A catalogue with no facets and no search still pays for the gaps around them; folder_buttons() renders an empty flex row unconditionally (view.rs:355-359).

Directions

Four ways to spend less height. All four keep the same OPDS inputs — page.search, page.levels, page.navigation, page.facets — and only change where they sit.

A · One toolbar line

Breadcrumb and controls collapse into two thin lines. Search, facets and the subsection list all become peers on a single 32 px strip; navigation links move behind a Browse ▾ menu that lists them with their counts. The source title goes to the breadcrumb root, so the identity band disappears entirely.

B · Toolbar plus an active-filter line

A, plus one line that exists only while something is filtering the list: a removable chip per applied facet and a Clear. It answers "why am I seeing these results" in one place and gives a one-click way out — the thing the closed dropdowns cannot do. Zero height on an unfiltered page, so the common case pays nothing.

C · Filters as a side rail

Everything that narrows the list moves to a 150 px column beside the results, where it grows downward into space the books were never using. Facet options are visible without a click and counts read down a column. Costs horizontal room — at three publication columns that is one column lost — so it wants to collapse below STORE_PUBLICATION_TWO_COLUMN_BREAKPOINT_PX.

D · One filter button, everything in a popover

The toolbar is a single line no matter how many facets the catalogue declares: search, Browse ▾, and one Filters button carrying a count. Everything else lives in a popover that can be as tall as it likes, because it overlays the results instead of displacing them. The most robust against a catalogue that sends eight facet axes; the most clicks to change one thing.

What I'd build

B, with C's rail as the wide-window form. B is the smallest change from where the code already is — the facet dropdowns exist, so it is one toolbar row, one conditional chip row, and moving page.navigation into a Browse menu. That alone returns 307 px and gets a whole card above the fold.

The chip row is the part worth insisting on: it is the only option that makes CatalogLink::active mean something to the reader, and it is the only one where undoing a filter is a single click rather than reopening the control that set it.

C then becomes a progressive enhancement above STORE_PUBLICATION_THREE_COLUMN_BREAKPOINT_PX (1 232 px), where 150 px of width is affordable and the same facet data can render as a rail instead of a toolbar. D is the fallback if a real catalogue turns out to send more facet axes than a line can hold — worth measuring against the crawled catalogues before building.

New components this needs in ui-components, none of which exist yet: catalog_toolbar(), catalog_filter_chip(label, on_remove), catalog_chip_row(), and a browse_menu_button(count). The store page keeps composing and wiring, per the crate's page/component split.

Not answered from the code

  • How many facet axes do real catalogues send? The layouts differ mainly in how they fail at 6+. servers/opds-cache has crawled the curated set — the distribution of page.facets.len() would settle A vs D outright.
  • Is page.navigation navigation or filtering? I have treated the links as subsections that belong in a menu. If readers use them as a primary way to move through a catalogue, they deserve to stay visible and something else should give up the height.
  • Does the breadcrumb root reliably name the source? A collapses the identity band into it. If push_level (browse.rs:107) can produce a first level whose title is not the source's, the band has to stay.
  • Should a facet change reset pagination? Not a layout question, but a chip row makes filter changes cheap enough that landing on page 7 of a newly filtered list will start to be noticed.
