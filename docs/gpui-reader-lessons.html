Lessons from a real reader

GPUI is a state machine with a view.

The useful unit in GPUI is not “a component tree.” It is an owned piece of state, changed at explicit boundaries, whose current value is projected into elements. Once that is clear, entities, invalidation, custom elements, and background work fit together.

01 · Mental model

One immediate loop, one slower branch

User-visible state should complete its trip through GPUI immediately. Work that can wait—database writes, parsing, network access—branches away and later returns through an entity update only if it has a result the UI still needs.

input / eventA click, action, renderer event, or task result.
→
entity.updateChange the authoritative state synchronously.
→
cx.notify()Only when observable output changed.
→
renderDescribe the UI for that state.
slower branch ↘Queue persistence or computation after the visible mutation. Preserve ordering when operations depend on one another.
Entity

Owns a behavior

State, lifetime, subscriptions, and events that change together.

Render

Projects state

Builds elements from what is already true. It does not make it true.

Element

Owns geometry

Layout, prepaint, hit testing, and painting using final bounds.

02 · Entities and widgets

An entity is an ownership boundary

Use an Entity<T> when T needs independent identity: it is updated elsewhere, receives events, owns subscriptions or tasks, or survives while parents re-render. Do not create an entity merely to split a large render function.

Too mechanical

Every visual box becomes an entity

This creates duplicated models, synchronization calls, and unclear ownership without buying a useful lifetime boundary.

Idiomatic

Entity where behavior is independent

The reader shell owns publication state; the toolbar entity owns interaction and a small projected model; plain layout remains plain elements.

Widget is a role, not one concrete GPUI type. A widget may be an entity-backed Render object, a reusable element, or both. Choose from ownership needs first, appearance second.

Copied state is a warning sign. If both the reader and toolbar store progress, title, and history availability, name one source authoritative and one a projection. Synchronize at one explicit boundary:

reader → toolbar projectionepub/state.rs
fn sync_toolbar(&self, reason: &'static str, cx: &mut Context<Self>) {
    let model = self.toolbar_model(cx);
    self.toolbar_view.update(cx, |toolbar, cx| {
        toolbar.set_model(model, reason, cx)
    });
}
03 · Observational rendering

Render answers a question

render answers: “Given the state now, which elements should exist?” Treat it like a pure projection even though Rust and GPUI allow &mut self. Re-rendering should not save data, change another entity, set authoritative state, or trigger a chain of updates.

Effect during observation

Setting the window title in render

A repaint now changes external state. The effect may run repeatedly and its cause is hidden.

Explicit lifecycle effect

Set it when activating the reader

The title changes at the moment the window’s content changes, while render merely describes its body.

observational rendershape, don’t synchronize
impl Render for ReaderView {
    fn render(&mut self, window: &mut Window, cx: &mut Context<Self>)
        -> impl IntoElement
    {
        let document = match &self.load_state {
            LoadState::Loading => empty_document().into_any_element(),
            LoadState::Ready(view) => view.clone().into_any_element(),
        };

        reader_shell().child(document)
    }
}
Quick test: may render calculate whether a sidebar is visible?

Yes, if that is a cheap derivation used only to build this frame. No, if it writes the answer back as a second authoritative state or updates another entity. Derive freely; mutate deliberately.

04 · Invalidation

notify means the view changed

cx.notify() invalidates the entity’s observation. It is not a generic “something happened” signal and not a request to redraw one tiny rectangle. Notify after a mutation only when the entity’s observable output can differ.

conditional + semantic invalidationreader event handling
if self.can_history_back != back || self.can_history_forward != forward {
    self.can_history_back = back;
    self.can_history_forward = forward;
    self.sync_toolbar("history_availability_changed", cx);
}

Semantic reasons such as annotation_deleted or reading_progress_changed make invalidation measurable. A label like state_changed only confirms that the application has state.

Correctness first. Notify the entity that owns the changed projection. Measure render counts before introducing elaborate fine-grained entity boundaries.
05 · Layout and custom elements

The calculator should publish its answer

If an element decides column count from its final viewport, that element owns the truth. A parent should not duplicate the fitting formula from approximate window dimensions. Expose the observed geometry produced by layout or prepaint.

request_layoutDeclare constraints and obtain a layout id.
→
prepaintRead final bounds and compose geometry.
→
observationPublish column count or visible range.
→
paintDraw the prepared result for those bounds.
renderer-owned geometryhtml-view-gpui
let previous = self.layout_geometry;
let paint = self.compose_viewport_display_list(viewport);

if self.layout_geometry != previous {
    cx.notify(); // observers can now read the real result
}

// Reader popup placement consumes, but does not recalculate:
let columns = renderer.read(cx)
    .layout_geometry()
    .map_or(1, |geometry| usize::from(geometry.column_count));
06 · Async boundaries

Async work should not hold the UI hostage

An annotation should appear when the user clicks, not after SQLite replies. Mutate visible state and notify synchronously; queue the durable write afterward. If writes are order-dependent, serialize them even when the worker pool is parallel.

optimistic mutationepub/state.rs
self.marks.append(annotation, "save annotation");
notify(cx, Component::ReaderShell, "annotation_created");
Loads

Return through the owner

Compute off-thread, then use the entity handle to install the result.

Writes

Preserve intent order

Create then delete must reach storage in that order, regardless of worker count.

Staleness

Check identity

Use a generation or request key when an older result could overwrite a newer request.

Choose a failure policy explicitly. The reader currently keeps optimistic state and logs persistence failures. Other domains may require rollback or an error badge. That is product behavior, not an async implementation detail.

07 · Focus and events

Express semantic ownership

Keyboard behavior follows focus, so a composite widget should define what “focus this widget” means. The reader’s semantic focus target is the document—not whichever container happened to receive a click.

one focus invariantepub/render.rs
impl Focusable for ReaderView {
    fn focus_handle(&self, cx: &App) -> FocusHandle {
        self.document_focus(cx)
            .unwrap_or_else(|| self.focus.clone())
    }
}

Likewise, use typed actions for commands and typed events for child-to-owner communication. Raw callbacks are fine for local glue, but shared behavior becomes easier to route, test, and reason about when its meaning has a type.

08 · Review checklist

Questions to ask in code review

01

Where is the single authoritative value for this behavior?

02

Does this type need its own identity and lifetime, or is it only visual structure?

03

Can render run repeatedly without changing application or external state?

04

Does every notification correspond to a possible observable change?

05

Is layout-derived information produced by the code that performs layout?

06

Does the UI update immediately while slow work follows a clear ordering and failure policy?

07

Could an old async result overwrite newer intent?

08

Does focus land on the semantic keyboard owner after overlays close?

The compact rule: Events mutate entities; entities notify; render projects; elements lay out and paint; background tasks persist or compute.
