A ten-minute mental model

from state
to pixels.

GPUI is easiest to understand as three cooperating systems: app-owned state, disposable UI descriptions, and explicit invalidation. Learn those boundaries and the API becomes much less mysterious.

01 / OWNApp owns long-lived state in entities.
02 / DESCRIBERender turns current state into elements.
03 / INVALIDATEnotify() declares which state became stale.
01 — Mental model

Retained state. Immediate description.

GPUI calls itself a hybrid immediate/retained UI framework. Your application state persists inside entities. The element tree produced by rendering is temporary: GPUI lays it out, prepaints it, paints it, then recreates or reuses it as needed.

Entity<T>

Stable identity and long-lived state, owned by the app.

View

An entity with Render, or a renderable value with an identity.

Element

A short-lived node responsible for layout, interaction, and paint.

The practical rule: put durable application state in entities; return a fresh description of the UI from render; implement a custom Element only when you need direct control of layout or painting.
02 — Entities & contexts

A handle is not the data.

Entity<T> is a cloneable, typed handle. The App owns the actual T, so the handle can only read or mutate it when you also have a GPUI context. This central ownership lets GPUI control borrowing, lifetime, observation, and UI invalidation.

entity.rscreate · read · update
let counter: Entity<Counter> = cx.new(|_| Counter { count: 0 });

let n = counter.read(cx).count;         // shared access

counter.update(cx, |counter, cx| {       // exclusive access
    counter.count += 1;
    cx.notify();
});

Contexts are capabilities. App exposes global services and all entities. Context<T> wraps App and adds services tied to one entity: notify, emit, listeners, weak handles, and tasks. Window carries per-window state such as focus and input.

03 — Widgets, views & elements

“Widget” is a role, not one type.

In everyday GPUI code, a widget usually means either a stateful view or a stateless component. Choose based on where identity and mutable state should live.

Render

Stateful view

A T: Render stored as Entity<T>. It has stable identity, a Context<T>, and its own invalidation boundary.

RenderOnce

Stateless component

A consumed value that turns props into elements. Derive IntoElement; keep durable state elsewhere.

badge.rsa small reusable component
#[derive(IntoElement)]
struct CountBadge { count: usize }

impl RenderOnce for CountBadge {
    fn render(self, _: &mut Window, _: &mut App) -> impl IntoElement {
        div().rounded_full().px_2().child(self.count.to_string())
    }
}

The lower layer is Element: request_layout → prepaint → paint. GPUI’s div, text, images, lists, and canvas already live there. Most application code should compose those primitives, not implement the pipeline itself.

04 — Rendering & invalidation

Mutation is silent until you notify.

update gives you mutable access; it does not imply a visual change. Call cx.notify() after a mutation that affects rendering. In this fork, GPUI tracks which windows display the entity and invalidates that view’s subtree.

updateMutate entity state inside its context.
→
notifyWake observers and mark displayed view state dirty.
→
renderDescribe the affected UI again from current state.
counter.rsthe essential loop
impl Render for Counter {
    fn render(&mut self, _: &mut Window, cx: &mut Context<Self>)
        -> impl IntoElement
    {
        div()
            .child(format!("Count: {}", self.count))
            .on_click(cx.listener(|this, _, _, cx| {
                this.count += 1;
                cx.notify();
            }))
    }
}

Optimization is explicit. An entity embedded as a child is a reactive boundary. Calling entity.cached(style) goes further: GPUI can reuse that subtree’s layout and paint work until the entity notifies or its external bounds/text style change. Because cached content is not measured, give it a definite size.

05 — Data flow

Observe state; subscribe to meaning.

GPUI has two deliberately different communication channels. Their distinction keeps state propagation predictable.

observe + notify

Something changed

The callback receives the entity handle and reads its latest state. Use this for derived state and view refresh.

subscribe + emit

Something happened

The callback receives a typed event. Use this for semantic occurrences such as “saved” or “selection confirmed.”

ownership_post.rsstate signal
cx.observe(&counter, |summary, counter, cx| {
    summary.total = counter.read(cx).count * 2;
    cx.notify();
}).detach();

A Subscription disconnects when dropped. Store it when lifetime matters; use .detach() only when the entities’ lifetimes are the intended lifetime. For async work, cx.spawn supplies a WeakEntity and an async context; re-enter through update after an await, because the entity may already be gone.

06 — Working rules

The habits that make GPUI click.

01

Model shared or long-lived state as an Entity; pass cloned handles, not copied state.

02

Use RenderOnce for small prop-driven components and Render for stateful views.

03

Keep render declarative. Put mutations in named methods or event listeners, then notify.

04

Use observe for state invalidation and typed events for intent. Keep those concepts separate.

05

Treat element IDs and entity IDs as identity: they anchor focus, local element state, and subtree reuse.
