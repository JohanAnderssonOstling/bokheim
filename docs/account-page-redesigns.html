Bokheim · account page · four directions

Account page redesigns, drawn at both widths

Decided: B · Identity-led for the account and storage, then C · Activity-led underneath, and the whole thing now lives inside Settings rather than at a destination of its own. B's donut was not built — the flat segmented track carries the quota, since GPUI has no conic gradient and the arc would be a canvas element for no gain in what it tells you.

Four ways to build the account and sync page so one element tree serves a 1000 px desktop window and a 390 px phone. Each direction is drawn twice from identical markup; the only thing that differs between the two frames is the width of the content area. HTML and CSS are the drawing — the shipping page is GPUI, and the container queries here stand in for a width the GPUI page measures for itself.

The content of the page is fixed across all four: who is signed in, what the quota is and how it is spent, each library's sync state and size, and the batch-transfer activity. What differs is which of those the page leads with.

The four directions at a glance

DirectionLeads withBest whenCost
A · Verdict One sentence answering "is everything synced?", then the evidence The common case is "nothing to do" and the page is a glance, not a visit Dense; the library table needs a real reflow to survive 390 px
B · Identity Who you are and a quota donut; libraries as cards The page doubles as the place you manage the account itself (plan, email, devices) Sync state gets demoted to a tag; slower to answer the sync question
C · Activity A timeline of what synced, uploaded and failed Users distrust sync and want to see it working Storage becomes a strip; needs real event history to not look empty
D · Settings list Grouped rows, each drilling into a detail pane Phone-first, and the account page keeps growing new settings Everything is one tap away instead of on screen; weakest at a glance

A · Verdict-led

The page opens with its conclusion. Below it, each block is evidence for that line: the quota as one shape, the libraries sorted by what they occupy, transfers folded into a footer until they have something to say. This is the closest to what ships today, rebuilt so the library row reflows instead of scrolling sideways.

C · Activity-led

Sync is a background process people don't believe until they see it. This direction makes the event log the spine of the page: what is running now, what finished, what failed and why. Account identity and quota compress into one strip at the top, and per-library state is read off the events rather than a table.

Narrow changes: the strip wraps so the meter takes its own line and the sync button moves to the top bar. The timeline itself is width-independent — one column at any size — which makes this the cheapest direction to make responsive and the one most exposed to an empty history.

D · Settings list

Every account concern becomes a row in a grouped list: identity, storage, each library, transfers, devices, sign-out. On a phone the rows are the page and each pushes a detail view. On desktop the same list becomes the left pane of a master/detail split, so nothing has to be redesigned to gain a second column — it just stops being hidden.

Building whichever one wins, in GPUI

  • There are no container queries. Measure the content area and branch on it. The cheapest route is a narrow: bool on SyncPage, fed from the root's size observation and handed to the component constructors in ui_components::account. One threshold, one constant, one if.
  • Branch inside components, not in the page. verdict_banner, storage_figures, usage_column_headings and the row builders take the flag and choose flex_row() or flex_col(). The page's composition stays identical at both widths, which keeps to the convention that pages compose and components style.
  • A's two-line row is a wrap, not a second widget. Use flex_wrap() with USAGE_AMOUNT_WIDTH released and the bar given w_full(); do not grow a parallel compact_library_row. The data-label trick becomes a muted text child added only when narrow.
  • B's donut needs a real arc. GPUI has no conic-gradient; it is a canvas/path element or a pre-rendered sprite. Costed against A's flat track, that is the main implementation price of B.
  • C's timeline needs history the backend does not keep yet. Transfers are reported as live groups plus a short completed list; a spine that reaches back to "yesterday" implies persisting events. Treat that as a backend change, not a UI one.
  • D's split is the same list twice. Render the list unconditionally; render the detail pane only when wide, and push it as a route when narrow. Nothing about the rows changes.
  • Units. Meter and bar heights, stripe width, dot sizes, all gaps and padding stay in px; text stays in rems(x / 16.0) so it follows the UI font, exactly as account.rs does today. The breakpoint itself is a fixed px constant.
  • Chrome is out of scope. The rail and the tab bar belong to the shell. The account page renders the scrollable content column and must not assume either exists.
