Bokheim · signed-out flows · four directions

Login and account access, drawn at both widths

Decided: L1 · One card, built in universal/sync/view.rs. The inputs carry placeholders and no labels, secondary flows are links rather than a row of equal buttons, and the feedback line sits under the title so it is read above the action. The server is never selectable — L4's chooser is not built, and api_server_url() stays fixed.

The companion to account-page-redesigns.html, covering everything before there is an account to report on: sign in, create account, verify the six-digit PIN, request a reset, set a new password — plus the error and busy states each of them can land in. Four directions, each drawn on desktop and phone from the same markup. The shipping page is GPUI; the container queries here stand in for a width it measures itself.

The flows that have to fit

Taken from AccountFlow and authentication.rs — these are the real states, not invented ones. Two of them are gated on what the server advertises, so any direction has to survive their absence.

Two constraints fall out of this and apply to every direction below. Password recovery is only offered after a sign-in has actually failed, so the first screen a user sees has one or two actions, never three. And the reset token arrives by email as text the user pastes — it is not the six-digit PIN, and the two must not look like the same control.

L4 · Server-first

Bokheim can talk to a self-hosted server, and which server you are on decides whether registration and password recovery exist at all. This direction makes that explicit: the server is a persistent line above the form, confirmed once and then quiet, with the actions below it driven by what that server advertises.

Details that apply whichever direction wins

  • Recovery appears after failure, not before. The first screen carries sign-in and, if the server allows it, create-account. "Forgot your password?" is revealed once login_failed is set — which is what the code does today and what keeps the first screen to two actions.
  • The PIN and the reset token are different objects. Six boxes for the PIN; a single monospace field with a paste affordance for the token. Drawing the token as an OTP grid invites people to type six of its characters and give up.
  • Say what happens without an account. Reading works offline and unsynced; every direction above says so once, quietly, so the screen does not read as a wall.
  • Errors sit above the button, inside the card. They are read on the way back to the action that produced them. Success messages take the same slot rather than a second one.
  • Busy disables the primary action and names what is happening — "Signing in…", "Creating account…", exactly the strings authentication.rs already sets.

Building it in GPUI

  • One narrow: bool, measured once. No container queries exist; the field pair chooses flex_row() or flex_col() from the same flag the signed-in page uses, and the button row does the same.
  • The flows are already a state machine. AccountFlow is the switch; none of these directions adds a state, they only change what each state renders. L3 splits sign-in into two screens, which means one extra variant (email captured, password pending) and nothing else.
  • L2's hero is a separate element, not a squeezed pane. Render the pane when wide, the crest when narrow, and keep the copy in one place — a slice of strings both read — so they cannot drift.
  • L4 needs a capability probe before the form. The contract's capabilities already carry public_registration, email_verification, resend_verification and password_recovery; the chips draw straight from them, and the reachability dot needs a cheap ping the backend does not expose yet.
  • Units. Field heights, gaps and padding in px; all text in rems(x / 16.0) so it follows the UI font, as account.rs does. L3's large type is the one place to add a new text size constant rather than reusing TITLE_LG.
  • Focus and submit. Enter advances every one of these screens; the OTP field auto-advances between boxes and submits on the sixth digit. That is behaviour, not layout, and it is the same in all four.
