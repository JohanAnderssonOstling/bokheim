What is wrong, and what replaces it.

Four concrete problems remain in shutdown persistence, updater state and session storage. Each finding below pairs the existing defect with a replacement structure.

2 mediumShutdown draining and update availability lack one owned lifecycle.

01 · Application lifetime

The session drains; reader writes do not promise to.

3

Quit flushes only one persistence producer

Medium

The app-quit callback synchronously flushes SessionSaveScheduler. Reader positions deliberately wait 250 ms before dispatching, annotation mutations have their own channel, and audiobook positions have another debounced channel. Those producers expose no drain contract to the application shell.

lib.rs:472–477 · reader persistence
UiSessionDeadline cleared; newest snapshot dispatched and awaited.
✓
reader / marksMay still be waiting in a debounce or mutation channel.
?
audiobookDrop sends a final position, but its receiver is not drained here.
Sharing the same one-thread blocking worker does not fully solve this. FIFO ordering helps only after a producer has dispatched its job; a position still inside a 250 ms debounce can be enqueued after the session flush.

Replace with

Give active durable writers a flush/close_and_drain operation and let the shell await all of them during quit. The shell should own the shutdown contract even when individual writers remain in reader and audiobook crates.

02 · Reactive state

Updater capability and updater state are conflated.

4

Automatic update state lives outside GPUI’s graph

Medium

DesktopUpdater stores available_update in an Rc<RefCell<_>>. The startup task mutates that cell without notifying an entity. SettingsPage only copies it when constructed, so an already-open page cannot observe the automatic result.

update_notice.rs:11–36 · services/app.rs:26–62

Replace with

ConcernBest representationReason
Check / install / restartPlain service callbacksCapabilities do not render and need no entity identity.
Idle / checking / available / installingEntity-owned update storeMultiple views and notifications need one observable state machine.
Current requestStored task or generationAutomatic and manual checks should not race to publish stale state.

The startup notification and settings page should consume the same store. That removes the copied snapshot and makes “available update” a normal GPUI projection.

03 · Session persistence

Persistence has conflicting authority and unsafe replacement.

5

Shared reader settings have two durable authorities

Low

Every reader preference snapshot is written into UiSession, while shared fields are also patched into the backend. At startup, backend values overwrite the corresponding session fields. A backend patch failure is only logged, so the session can show the new value now and silently revert to the backend value next launch.

lib.rs:224–302

Replace with

Split local shell preferences—such as TOC width and visibility—from backend-owned reading preferences, or document one store as a cache with an explicit reconciliation/error policy.

6

The session file is replaced in place

Low

The final save uses fs::write directly on the authoritative JSON file. A crash or full disk during replacement can leave truncated JSON, after which startup discards the whole session.

session.rs:56–91, 117–180

Replace with

Write a sibling temporary file, flush it, then atomically rename it over the session file. This is durability hardening rather than a GPUI entity change.

Only defects and direct replacements are included. Scope: apps/desktop-gpui plus directly connected persistence and updater state contracts.
