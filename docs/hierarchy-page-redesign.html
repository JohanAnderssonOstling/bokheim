What I'd build

A now. It needs no backend work, fixes the defect, lands identically on both frontends, and is denser than what is there today rather than the trade the other three ask for. C is less a layout than an admission the app owes the reader: ship the toggle and the dashed buckets even if the chips never happen. B is the best desktop answer and wants A's groundwork first.

  1. Take the count out of the label string into its own element; totals only.
  2. Replace the wrapping button row with the fixed-column grid above.
  3. Separate children from books with a rule, not a pair of headings.
  4. Decide downloaded_book_count's fate: spend it on a folder-download affordance, or stop sending it.
  5. Point desktop's box at search_folder / search_subject, then delete the Search page.
  6. Mark the synthesized subject buckets as synthesized, wherever they render.

Decided: one search, and the Search page goes

The box searches every book under the current node — the folder and its subfolders, the subject and its subsubjects — on both frontends. At the root that scope is the whole library, which is what the Search page was for, so the Search page stops having a job.

This is mostly deletion. The backend already implements it and mobile already uses it:

Two consequences worth taking deliberately. Desktop search becomes a database round-trip instead of an in-memory filter, so it needs the debounce the contract already carries (search_debounce_ms 220) and results are capped at search_result_limit 100. And the box stops filtering the children: today typing narrows the folder list too. Under the new rule a query returns books from anywhere beneath, so the child list either stays put or hides while a query is active — the mockups above hide it.

Not answered from the code

  • Is a folder's book_count recursive? The download queries provably are; I did not trace the browse counts. If it isn't, A's zone headings need different copy.
  • Should desktop gain the folder download action? The contract carries download_folder_label; mobile's FolderCard uses it, the desktop card offers only "open".
