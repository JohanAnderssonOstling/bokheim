Bokheim · design system · proposal

A general revamp: colour, spacing, type, borders, layout

Measured against the GPUI tokens and the retired shared-token definitions that existed when this proposal was written. Every number below was either read out of those sources or computed from the exported palettes — the contrast ratios are WCAG relative luminance, not impressions.

The diagnosis in one line: the interface is separated by borders instead of by surfaces. Card and page differ by a contrast ratio of 1.10 — effectively the same colour — so every boundary has to be drawn as a 1 px line at 3.6:1 (light) and 4.7:1 (dark), which is text-level contrast. The result reads as a wireframe grid. Fix that one relationship and most of the rest — border roles, radius, density — follows.

What changed between the two: the page darkened so cards lift off it; card edges dropped from 3.6:1 to 2.6:1; row dividers dropped to 1.7:1 and no longer compete with the text they separate; meter and bar wells use a sunk surface instead of the page colour; body text came down from 14.2:1 to 11.5:1; library names moved from 600 to 500 so the section headers can keep 600; controls picked up a 4 px radius while surfaces stayed square.

4 · Spacing, margins and padding

The scale is 2 / 4 / 8 / 16 and stops. Everything a page actually needs above 16 is improvised, so section rhythm differs per file. Two additions fix it: the missing 12, and a large end of the scale.

xxs 2hairline gaps, tag padding
xs 4label→value, icon→text
sm 8inside a row, between buttons
md 12 · newrow padding, form field gap (13 ad-hoc uses today)
lg 16card padding
xl 24 · newbetween cards, page gutter
2xl 32 · newbetween page sections
3xl 48 · newpage top margin, empty-state breathing

Rules that go with it

  • Padding is a surface's own property. Cards 16, rows 12/8, controls 8/12. A page never adds padding to compensate for a component that lacks it.
  • Gaps come from the scale, never from a margin. Flex/grid gap only — no stray margin-bottom creating collapsed-margin surprises across the GPUI and web frontends.
  • The page gutter is 24 expanded, 16 compact, and matches the gap between cards, so the outer margin never looks tighter than the inner rhythm.
  • Anything above 48 is a dimension, not spacing — a control height, a column width, a measure — and gets a named constant, as tokens.rs already does for SETTINGS_CONTROL_HEIGHT and friends.
  • Keep the current px/rem split: sizes that must scale with the UI font stay in rems(x / 16.0), gaps and padding stay in px. That rule is already right and should survive the revamp.

5 · Typography

Six sizes today, but 12 and 13 are one pixel apart, so the working scale is really four sizes plus two headings. A ~1.2 ratio gives six that are all distinguishable, with a 1:1 mapping onto the existing names.

xs 12 → 12Detail lines, captions, legends
sm 13 → 14Row titles, secondary body
md 15 → 16Body, form fields, buttons
lg 17 → 20Card headings, identity
title_md 21 → 26Section titles
title_lg 28 → 32Page titles

Weight and leading

  • Three weights, not two. 400 body · 500 item titles · 600 section headers. Today 600 is used 36 times and 500 once, so every list title shouts as loudly as the heading above it. Demoting rows to 500 is the single cheapest legibility win in the whole proposal.
  • 700 is reserved for the one page title, if used at all.
  • Add leading tokens: LEADING_TIGHT 1.2 (titles), LEADING_NORMAL 1.45 (interface body), LEADING_LOOSE 1.6 (reader prose). None exist outside the book card today, so multi-line detail text sets at whatever the platform default is.
  • Use the serif you already ship. design_tokens.json defines a serif family that the native chrome never uses. Setting section and page titles in it — sans for everything functional — gives the application a voice that matches a library, at zero cost.
  • Numerals in tables should be tabular: the storage columns are compared down the column, and proportional digits make them ragged.

6 · Borders, radius, elevation

  • Resolve the radius contradiction first. The native app is square by an argued decision (SURFACE_CORNER_RADIUS_PX = 0); the exporter ships 8 / 11 / 16 to the web frontend from a hardcoded array. Recommendation: keep square surfaces — it is distinctive and suits the subject — but give controls 4 px so buttons, inputs and tags read as pressable, and export exactly that: { none: 0, control: 4, pill: 999 }.
  • A card on a differentiated page does not need an outline. Once page/card sit at 1.22, drop the card border entirely on the settings and account surfaces and keep only the internal hairlines. Keep the outline where a surface sits on the same colour as itself — popovers, the library switcher.
  • One shadow, unchanged. overlay_shadow for things that float; never for cards. That rule is already in tokens.rs and is worth keeping verbatim.
  • Focus is border_strong, not accent. A 2 px accent ring on a green-accented palette disappears against primary buttons; the strong border reads on every surface.
  • Hairlines never cross a padding boundary. Row dividers stop at the card's padding, so the card edge stays the only full-bleed line.

7 · Layout and measure

  • Name the three measures: MEASURE_FORM 420 (auth, single-column forms), MEASURE_SETTINGS 720, MEASURE_PAGE 920. Today the first does not exist, and the other two are inline literals in layout.rs and browser.rs.
  • 720, not 580, for settings. Now that the account section lives inside Settings, its library rows carry two 76 px amount columns plus a 96 px comparison bar — 248 px of fixed columns inside a 580 px measure, leaving ~300 px for names that were designed against 920. This is a real regression from moving account into settings and it is worth fixing with the revamp.
  • Forms stop at 420. A sign-in field 700 px wide reads as a search box. The auth card should centre at form measure inside whatever page it lives on.
  • One breakpoint, already defined. WindowWidthClass exists and is the right place for every narrow/wide decision; nothing new is needed for the revamp.
  • Vertical rhythm from the scale: 32 between page sections, 24 between cards, 16 inside a card, 12 for rows. Every one of those is a token after §4, so a page cannot invent its own rhythm.

8 · How to land it

Ordered so each step is independently shippable and independently revertible. Steps 1–3 are where nearly all the visible improvement is, and none of them touches a single call site.

#StepTouchesRisk
1Repaletteapp-preferences palettes: page_bg, ink_text, border → new valueslow — values only, no call sites
2Split the border roleBrowserTheme + hairline, border_strong, surface_sunk; point row dividers at hairlinelow — additive; existing border keeps working
3Demote row weightsSEMIBOLD → MEDIUM in item_identity, book cards, list rowslow — mechanical
4Extend the spacing scaleSPACE_MD 12, SPACE_LG 24, SPACE_XL 32, SPACE_2XL 48; migrate the ~22 ad-hoc 12/20 usesmedium — renames SPACE_MD's meaning, so do it in one commit
5Retune the type scaleTEXT_SM 13→14, TEXT_MD 15→16, TEXT_LG 17→20, TITLE_* 21/28→26/32medium — every page grows slightly; check the Kobo screen first
6Leading + serif titlesLEADING_* constants; serif family on section/page titlesmedium — needs the font shipped in assets
7Radius decision + exporter fixdesign_tokens.rs RADIUS array, nav_item_height mislabellow — but coordinate with the web frontend
8Named measureslayout.rs, browser.rs; settings 580 → 720low

One caution specific to this codebase: SPACE_MD currently means 16 and is used everywhere as card padding. Introducing a 12 as the new SPACE_MD would silently re-space the entire application. Add SPACE_SM_PLUS/SPACE_LG-style names around the existing ones instead, or rename in a single mechanical commit with no other change in it — but do not mix the two.

A second caution: the Kobo build runs the same components at a different physical size and on e-ink, where the proposed hairline at 1.7:1 may vanish entirely. Before step 2 lands, check the e-ink path — it may want to keep the current strong border as a device-specific override rather than inherit the softened one.
